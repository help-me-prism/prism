# AI 호출·병렬 처리·메모리 하네스 검토

2026-09-12 · 현재 구현과 이번 변경 기준. 기본 모델을 강제로 바꾸지 않고 실행 제어, 근거 검증, 입력 구성부터 개선했다.

## AI가 실제로 쓰이는 곳

앱은 OpenAI/Anthropic API를 직접 호출하지 않고 로그인된 Codex/Claude CLI를 이용한다. 검색·PDF 파싱·LaTeX/JATS 구조화·근거 좌표 추출·그래프·일반 노트 저장은 모델 없이 처리한다. 사용 기록의 `structure` 분류는 남아 있지만 현재 그 분류로 모델을 호출하는 실행 경로는 없다.

## 번역 병렬 처리의 판단

### 여러 논문

가능하며 서로 다른 논문의 번역 작업은 기존에도 동시에 시작할 수 있었다. 문제는 논문마다 3개씩 실행하여 N편에서 최대 3N개의 CLI가 시작될 수 있었다는 점이다. 이번에는 번역·읽기 안내·메모리·노트 정리가 **제공자별 전체 3개 슬롯**을 공유하는 FIFO를 거치게 했다. Codex와 Claude는 각자의 큐를 사용한다. 채팅은 별도 전송 경로라 이 큐를 기다리지 않는다. 실제 계정 한도는 채팅과도 공유될 수 있으므로 이 값은 사용 한도 보장이 아니다.

여러 편을 열어 번역을 시작하면 백엔드에서 계속 처리된다. 이번 변경에 라이브러리 다중 선택·일괄 번역 버튼을 새로 추가한 것은 아니다.

### 한 논문 안

이미 최대 3개 묶음을 병렬로 처리하고 있었다. 이번에는 설정 → 작업별 AI → **논문 하나의 동시 번역 수**에서 1·2·3 중 고를 수 있다. 변경 값은 다음 번역 실행부터 적용한다.

각 요청은 독립적인 CLI 실행이며, 이전 번역 응답에 의존하지 않는다. 이 조건에서는 병렬화가 적합하다. 이번에는 들어갈 수 있는 문단을 한 묶음으로 유지하고, 너무 긴 문단만 문장 단위로 나누되 문단·앞뒤 원문을 계속 제공한다. 기본 예산은 원문 약 9,000자, 직렬화된 전체 프롬프트 최대 24,000자다. 단일 문장의 예외도 전체 프롬프트 상한을 넘으면 호출 전에 거부한다.

```mermaid
flowchart LR
  P[여러 논문] --> B[원문 캐시 검사 · 문단별 묶기]
  B --> Q[제공자별 FIFO · 전체 3개]
  Q --> W[독립 CLI 요청]
  W --> V[ID · 숫자 · 수식 · 인용 검사]
  V --> R[실패한 문장만 한 번 재시도]
  V --> S[논문별 저장 직렬화]
  R --> S
  S --> F[원자적 캐시 교체 · 진행률 갱신]
```

모델 응답은 완료 순서로 저장할 수 있지만 원문 ID로 복원하므로 문장 순서는 바뀌지 않는다. 파일 저장은 논문별로 직렬화하고 원자적으로 교체한다. 취소는 대기 중인 호출과 실행 중인 자식 프로세스에 전파한다. 첫 실패 뒤에는 해당 논문의 추가 호출을 중단하고 이미 저장한 결과를 보존한다. 앱 종료·창 닫기도 대기열을 취소한다.

### 무제한 병렬화를 권하지 않는 이유

- 동시 실행은 대기시간을 줄일 수 있지만 입력·출력 토큰을 자동으로 줄여 주지 않는다. 너무 작은 묶음은 공통 지시와 문맥, CLI 시작 비용을 더 자주 반복한다.
- 논문 전체의 용어 선택은 아직 하나의 공유 용어집으로 고정하지 않는다. 문단 경계와 원문 문맥은 불일치를 줄이지만, 병렬 결과 사이의 번역어가 항상 같다는 보장은 없다.
- 제공자 사용 한도·네트워크 지연·작업 크기 차이 때문에 3배 빨라진다고 단정할 수 없다. 계정이 혼잡하면 동시 번역 수를 낮추는 편이 유리할 수 있다.
- 표·독립 수식·손상된 PDF 문단은 원문 보존이 우선이다. 병렬 호출 수를 늘려도 추출 오류가 해결되지는 않는다.

용어 일관성이 특히 중요한 분야라면 다음 확장은 **사용자 용어집 또는 논문별 검토된 용어집을 모든 요청에 같은 버전으로 제공**하는 방식이 적절하다. 모델로 용어집을 먼저 만들면 선행 호출과 검토 비용이 추가되므로 기본 동작으로 도입하지 않았다. 도입 시 캐시 키에 용어집 버전을 포함하고, 용어집 생성 → 독립 번역 → 문제 구간만 검토 순서를 사용해야 한다. 순차 실행만으로는 독립 CLI 사이에 기억이 공유되지 않으므로 용어 일관성 문제가 저절로 해결되지 않는다.

## 자동 기억: 프롬프트와 코드가 맡는 역할

이전 구현은 `previous + note[:10000] + question[:4000] + answer[:5000]`을 보내고 모델의 `items` 전체 목록으로 교체했다. 따라서 모델이 기존 항목을 빠뜨리면 삭제로 해석됐고, AI 답변이나 생성된 노트가 사용자 이해의 근거로 잘못 사용될 여지가 있었다.

새 흐름은 다음과 같다.

1. 완료된 사용자–답변 쌍만 처리하고 세션·볼트 소유권을 확인한다. 비교 대화처럼 둘 이상의 논문이 첨부된 경우 자동 저장을 건너뛴다. `primaryPaperId`는 첫 번째 선택이라는 이유만으로 귀속 증거가 되지 않는다.
2. 인사·일반 요약 요청은 저비용 정규식으로 걸러 모델을 호출하지 않는다. 이 단계는 후보 선별일 뿐 저장 여부를 결정하지 않는다. 4,000자보다 긴 발언은 끝의 정정·부정을 잃지 않도록 잘라 저장하지 않고 건너뛴다.
3. 모델에는 대상 논문 ID·제목, 이전 기억, 보호할 항목 ID, 이번 사용자 발언만 제공한다. 전체 노트와 AI 답변은 전달하지 않는다.
4. 목적·남은 혼란·적용 계획·결정·명시적으로 확인한 이해만 선별한다. 가정·인용문·다른 논문·일반 질문은 제외하고, 기본 응답은 `{"changes":[]}`다. 짧은 긍정·부정 예시를 프롬프트에 포함한다.
5. 추가/수정은 `upsert`, 삭제는 `remove`로 표현한다. 생략은 유지다. 모든 변경에 이번 사용자 발언의 정확한 연속 인용문을 요구한다. 삭제에는 기존 기억과 현재 인용문 양쪽에 있는 구체적인 주제도 요구하며, 미해결·삭제 금지 표현을 거부한다.
6. 코드가 JSON 형식, 허용 종류·ID, 중복, 인용문 포함 여부, 근거에 없는 수치, 최대 6개 기억, 최대 220자 본문을 확인한다. 잘못된 변경 목록은 저장하지 않는다. 새 기억 때문에 무관한 기존 항목을 밀어내지 않는다.
7. 추출 전후 노트를 읽어 사용자 수정·삭제를 보호한다. 저장 직전 revision을 확인하고 충돌 시 재확인한다. 같은 노트의 AI 갱신은 잠금으로 겹치지 않게 한다.
8. 기억별 `exchangeId + quote`를 파생 캐시에 보관한다. 채팅에서 다시 읽을 때는 캐시보다 실제 Markdown 내용을 우선해 사용자의 수정·삭제가 반영되게 한다.

예시:

```json
{
  "changes": [
    {
      "op": "remove",
      "id": "memory-samples",
      "quote": "표본 수의 한계는 이제 이해했어.",
      "subject": "표본 수"
    }
  ]
}
```

이 연산은 표본 수 항목만 제거하며, 인과 추론에 대한 다른 의문은 그대로 둔다. “이제 이해했어”만으로는 어느 의문인지 확정하지 않는다. “아직 이해하지 못했으니 삭제하지 말아 줘”는 삭제 근거가 아니다.

구현: [memoryHarness.ts](../electron/memoryHarness.ts), [readingGuide.ts](../electron/readingGuide.ts). 기억 본문은 노트의 `prism:reading` 영역, 파생 상태는 `.prism/cache/reading-guide/<논문 ID 해시>.json`에 보관한다. 기존 상태는 유지하며 새 추출 응답부터 변경 연산 형식을 사용한다.

### 의도적으로 남긴 경계

정확한 인용문 존재는 **출처 검증**이지 의미가 반드시 따라 나온다는 증명은 아니다. 모델이 실제 발언을 잘못 해석하거나, 키워드 없는 중요한 의도를 놓칠 수 있다. 삭제 검사는 한국어·영어 표현에 보수적이어서 해소됐지만 항목이 유지되는 경우도 가능하다. 다중 논문·긴 발언을 건너뛰는 것도 잘못된 자동 저장을 줄이는 대신 재현율을 낮춘 선택이다.

수동 MCP `remember`는 기존 `confusion/asked` 섹션을 갱신하는 별도 계약이며, 자동 기억의 변경 연산 프로토콜로 전환하지 않았다. 이 도구에는 사용자 요청, 허용 섹션, 수정 보호, revision 검사를 적용한다. 자동 추출의 원문 인용 검사가 이 별도 도구까지 적용된다고 해석하면 안 된다.

## 공통 효율·정확도 개선

- [aiScheduler.ts](../electron/aiScheduler.ts): 제공자별 FIFO, 전체 동시 실행 제한, 대기 중 취소, 예외 후 슬롯 반환. 실제 채팅을 백그라운드 번역 큐 뒤에 세우지 않는다.
- [cliTaskResult.ts](../electron/cliTaskResult.ts): 프로세스 종료 코드 0만으로 성공 처리하지 않는다. Codex 최종 완료 이벤트, Claude 오류 결과를 확인한다. 실패 응답을 번역 품질 오류로 오인해 추가 재시도하는 것을 막는다. 공통 실행기에 3분 제한과 출력 크기 상한도 적용한다.
- [translationHarness.ts](../electron/translationHarness.ts): 원문에 없거나 중복된 수식·인용까지 거부한다. 기존 숫자·단위·부등호·표기 토큰 검사를 유지한다. 의미상의 부정·인과관계까지 결정론적으로 검증하는 것은 아니다.
- [modelGrounding.ts](../electron/modelGrounding.ts): AI 읽기 안내·자동 기억·자동 개요·저장된 AI 답변을 다른 생성 작업의 원래 사용자 메모/근거로 다시 투입하지 않는다. 실제 사용자 메모와 직접 PDF 근거는 유지한다.

후속 품질 평가는 분야별 번역의 부정·인과·비교 방향·전문 용어 일관성, 실제 장기 대화의 메모리 정밀도/재현율·해소 정확도·수정 보존을 분리해서 측정해야 한다. 새 모델이나 프롬프트를 적용할 때 같은 평가셋을 돌리고, 자동 생성된 판정만으로 품질을 인증하지 않는다.

공식 문서에서도 구조화 출력은 형식 준수와 내용 정확도를 구분하고, 실제 사례를 반영하는 반복 평가를 권장한다. 참고: [Codex 비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [평가 설계](https://developers.openai.com/api/docs/guides/evaluation-best-practices). 현재 앱은 CLI 출력과 로컬 검증을 사용하며 API의 strict JSON Schema를 적용했다고 주장하지 않는다.
