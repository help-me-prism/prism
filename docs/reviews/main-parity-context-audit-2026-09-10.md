# main 대비 기능·CLI 컨텍스트 검토

검토일: 2026-09-10. 비교 기준은 fetch 후 `origin/main`의 `d781f19`와 현재 `codex/product-reader`의 `ee056bf`. 분기점도 `d781f19`다. 로컬 main `b485a26`은 13커밋 뒤이므로 비교 기준으로 사용하지 않았다. 참조 작업 「프리즘 논문 리더 전면 개선」과 인계 보고서를 읽고 실제 diff·호출 경로를 확인했다.

이번 작업은 검토다. 제품 코드는 수정하지 않았고, 실제 모델 호출·페르소나 반복 검수·새 패키징은 하지 않았다. 아래의 권고는 구현 완료를 뜻하지 않는다.

## 판단

현재 결과는 기능을 크게 덜어낸 전면 재작성보다 **기존 제품에 읽기 품질·저장 안정성·새 UI를 추가한 개선판**에 가깝다. 비교 범위에서 삭제된 파일은 없고, 전체 diff는 문서·테스트·이미지를 포함해 304개 파일, +27,891/-1,623줄이다. 화면의 간소화와 코드의 간소화는 구분해야 한다. 특히 `electron/main.ts`, `src/App.tsx`, `src/PaperWorkspace.tsx`의 책임은 여전히 크다.

기존 기능 전체를 되돌릴 필요는 없다. 복원할 것은 **사용자가 논문 범위를 통제하는 능력과 지식 정리의 발견 가능한 동선**이다. 자동 AI 호출이나 의미가 부정확한 관계 변환은 되돌리지 않는 편이 낫다. CLI 효율성은 가벼운 기본 모델·발췌·캐시 수준까지 개선됐지만, 총 입력 예산·장기 대화 수명·실측 운영은 미완성이다.

## 2. 먼저 수정할 컨텍스트 결함

### A. 페이지를 첨부해도 해당 페이지 본문이 보장되지 않음 — P1

- 페이지 앵커의 source는 `Page 8 of paper` 같은 위치 문구다. `src/PaperWorkspace.tsx:473,958`.
- `compactAnchorContext`는 이 문자열을 전송하며 페이지의 원문 문장으로 확장하지 않는다. `src/paper/anchorContext.ts:3`.
- 자동 발췌는 사용자가 타이핑한 질문 문자열에서 페이지 번호를 찾는다. 선택한 페이지 앵커 자체를 우선순위로 받지 않는다. `src/paper/readerContext.ts:15`, `src/App.tsx:539`.
- 재현: 8쪽 첨부 + ‘이 페이지 설명해줘’에서 1쪽 초록이 3,000자 예산을 차지하고 8쪽 본문이 전혀 전달되지 않았다. 페이지 위치 문구만 남았다.
- 권고: 명시적 페이지/표/수식 선택을 최우선 입력으로 확장한다. 해당 페이지 원문이 부족하면 읽지 못한 범위를 표시한다. 페이지 메모의 위치 링크는 별개로 유지한다.
- 이 문제는 main부터 있던 페이지 placeholder 설계에서 이어진 미완성이고, 새 자동 발췌만으로 해결되지 않았다.

### B. 9번째 선택 논문이 조용히 누락됨 — P1

- UI 선택 개수 제한은 없지만 `readingEvidence`는 `.slice(0, 8)`, 논문 메타데이터도 `.slice(0, 8)`이다. `src/paper/readerContext.ts:54`, `src/App.tsx:540,759`.
- 재현: 9편 선택 시 마지막 논문이 excerpts와 missingPaperIds 양쪽에서 빠졌다.
- selectedPapers는 사용자가 고른 순서가 아닌 라이브러리 순서다. 많이 선택하면 현재 읽는 논문도 앞의 8편에 들어간다는 보장이 없다.
- 권고: 선택 단계에서 한도를 명시하거나 실제 포함·제외 논문을 전송 전에 표시. 활성/명시 선택 논문을 우선한다.

### C. 개별 근거 제한과 총 메시지 제한 불일치 — P1

- 자동 발췌는 9,000자, 직접 선택이 있으면 3,000자. 직접 근거는 건당 4,000자지만 개수·합계 예산은 없다. 초록은 논문당 1,200자 × 최대 8편이 별도로 붙는다.
- 재현: 서로 다른 직접 근거 13개 × 4,000자 → selectedEvidence만 53,197자. 질문과 다른 문맥이 붙기 전에 IPC의 50,000자 제한 초과. `electron/main.ts:1668`.
- 권고: 질문·직접 근거·자동 발췌·초록·도구 출력·예상 답변을 하나의 예산으로 계산. 직접 선택을 우선 보존하고 자동 발췌부터 줄인다. 읽지 않은 출처를 읽었다고 표시하지 않는다.

### D. 대화와 보관함의 소유권 — P1 추가 검증

- 대화는 userData의 단일 `sessions.json`에 저장되고 CLI thread를 재개한다. 보관함은 매 요청의 현재 설정에서 읽는다. `electron/main.ts:365–380,489,1672`.
- 백그라운드 `routeChatIntoNotes`도 전체 저장 대화를 읽고 현재 보관함에 적용한다. `electron/main.ts:520`.
- 코드상 세션의 vault 소유권 분리가 충분하지 않다. 다른 보관함으로 바꾼 뒤 같은 대화를 이어가면 이전 대화 문맥과 현재 도구 대상이 섞일 가능성이 있다. 이번에는 실제 쓰기 재현을 수행하지 않았다.
- 권고: 세션에 안정적인 vault ID를 연결하고 보관함 변경 시 새 세션 또는 명시적인 문맥 이관. 같은 논문 ID가 두 vault에 있는 테스트가 필요하다. 답변 저장 버튼의 vault 보호와 이 경로는 별개다.

## 3. CLI 효율성 평가

### 이미 좋은 부분

- 새 대화의 저비용 기본값은 Codex Luna / Claude Haiku. Codex 채팅과 일회성 실행에 low effort를 지정. 사용자가 다른 모델을 선택할 수는 있으나 실패 후 고급 모델 자동 승격 경로는 확인되지 않았다.
- 일반 채팅은 CLI thread/session을 재개하고 앱의 대화 전체를 매번 문자열로 재구성하지 않는다.
- 자동 발췌는 로컬 규칙 기반이며 별도 AI 검색어 재작성 호출이 없다. 한국어 질문의 일부 의도를 영어 검색어에 대응시킨다.
- 직접 첨부 근거는 같은 paperId+anchorId를 한 요청 내에서 중복 제거한다.
- 번역은 누락 문장 중심으로 실행하고 원문 일치·과학 표기 검사를 통과한 캐시를 재사용한다. 문단 문맥도 블록별로 중복 제거한다.
- 번역 범위 선택, 취소, 180초 타임아웃이 있고, 읽음 표시와 일반 설명에서 불필요한 AI 호출을 줄였다.
- 이미지 입력은 최대 4개·합계 20MB·이미지당 2,500만 픽셀 제한이 있다. 다만 이는 토큰 예산이 아니다.

### 아직 부족한 부분

1. **CLI 실행 환경이 일관되지 않다.** Codex 새 채팅은 userData + 앱용 baseInstructions지만 resume은 Documents로 cwd가 바뀐다. 번역/지식 제안은 매번 Documents에서 새 CLI 프로세스를 띄우고 모델·effort·sandbox만 지정한다. 사용자 설정·기본 도구·주변 지침이 작업 입력에 얼마나 붙는지 앱이 계측하거나 격리하지 않는다. 실제 유입량과 원인은 설치별 측정이 필요하다. `electron/main.ts:371,373,878`.
2. **짧은 작업도 큰 기본 입력을 부담할 수 있다.** 이전 round32 기록은 두 문장 번역 한 번에 입력 13,006 / 캐시 입력 8,960 / 출력 223토큰이었다. 이번에 새로 측정한 수치는 아니며 모든 요청의 평균도 아니다. 캐시 비중이 있으므로 전체를 신규 과금 입력처럼 해석하면 안 된다. 그래도 모델 이름만으로 효율성을 판단할 수 없다는 근거다.
3. **턴 사이 근거 중복을 관리하지 않는다.** 같은 질문/후속 질문에도 초록·관련 발췌·지시문을 다시 붙인다. CLI의 캐시 적중과 앱이 중복 내용을 덜 보내는 것은 다른 문제다. 세션 내 출처 해시·리비전과 마지막 제공 범위를 추적하고, 압축 후에는 필요한 근거를 다시 주입하는 설계가 필요하다.
4. **앱 차원의 대화 압축·재시작 정책이 없다.** 사용량 게이지는 있으나 임계치에 따른 요약/새 세션 이관/근거 재구성 정책은 찾지 못했다. CLI 자체 압축 기능 유무를 부정하는 뜻은 아니다. 현재 앱은 그 수명과 결과를 검증하지 않는다. `compactSessions`는 이미지 preview를 저장에서 빼는 코드이며 LLM 문맥 압축이 아니다.
5. **문자 수 제한을 토큰 예산으로 사용한다.** 번역 배치는 source 9,000자를 기준으로 나누지만 문맥은 별도 최대 8,000자가 붙고 JSON·보호 토큰·시스템 문맥은 추가된다. 긴 단일 문장은 batch 상한을 넘을 수도 있다. `electron/main.ts:933`, `electron/translationHarness.ts:45`.
6. **작업별 실제 사용량이 사라진다.** 번역/지식 제안 실행은 최종 텍스트만 추출하고 usage를 보관하지 않는다. 채팅은 context 수치 위주이며 입력·캐시·출력·지연·실패 비용의 누적 기록은 없다. Claude result usage 합계를 현재 context 점유로 사용하는 것도 여러 도구 호출이 있는 턴에서 정확한지 프로토콜 fixture로 검증해야 한다. `electron/main.ts:322,475,878`.
7. **반복 실행·이미지 비용에 공통 정책이 없다.** UI의 digesting/suggesting 방어는 있지만 백엔드 지식 실행 jobKey는 매번 timestamp라 동일 입력의 공통 중복 실행 방지/결과 캐시가 아니다. 큰 이미지 원본을 그대로 전송하므로 글자를 읽을 최소 해상도와 고해상도 재요청 정책도 필요하다. 모델별 이미지 과금량은 이번 검토에서 측정하지 않았다.

우선 구현할 것은 `작업 종류 + 모델 + 입력 구성별 크기 + 실제 input/cache/output + 지연 + 성공/실패` 기록이다. 그 뒤 같은 고정 표본으로 일반 채팅/번역/지식 정리의 실행 환경을 비교한다. 임의의 모델 교체부터 하면 개선 원인을 알 수 없다.

## 4. 사람이 피드백할 작업 묶음

각 묶음은 **하나의 검토 빌드 + 바뀐 점 3개 이내 + 고정 시나리오 + 알려진 한계**로 전달한다. 자동 테스트와 파일 보존 검사는 개발자가 먼저 끝낸다. 사람은 사용감·내용을 판정한다. 새로운 문제가 없는 통과 항목은 다시 전체 검수하지 않는다.

| 순서 | 개발자가 먼저 끝낼 범위 | 사용자가 할 피드백 | 이 묶음의 완료 기준 |
|---|---|---|---|
| 0. 검토 기반 | 최신 CI의 임시 경로 정규화 실패 수정, Windows/Mac 전체 검사 확인 | 없음 | 동일 커밋의 자동 검사 통과. 빌드와 소스 커밋 일치 |
| 1. 질문 범위·비용 | A/B/C 해결, 현재 논문 해제 복원, vault 경계 검증, 작업별 사용량 기록 및 일회성 CLI 실행 환경 정리 | 약 15분. ‘이 페이지 설명’, 문장 설명, 피겨 질문, 두 논문 비교를 각 1회. AI가 본 범위와 답변의 근거가 맞는지 표시 | 화면에서 선택한 자료와 실제 요청의 자료 일치. 빠진 자료는 명확히 안내. 호출 수·토큰·시간 기록 |
| 2. 읽기·번역·피겨 | 비교/복귀 위치 보존, 번역 품질 결함, 캡처 접근성. 범위 제한 재번역 동선 검토 | 약 20분. 익숙한 분야 논문 1편의 초록·방법·수식/표/피겨 각 한 곳. 원문과 번역 대조. 어려운 PDF 1편은 필요한 부분만 추가 | 부정/수치/단위/주장 강도·문장 누락 확인. 보존된 원문과 번역을 구분. AI가 임의로 품질 합격 처리하지 않음 |
| 3. 지식으로 남기기 | 읽음 후 연결 제안 진입점, 이해 상태 명시적 기록, 답변→메모→주장→근거 왕복, 무료 일괄 갱신 동선 | 약 20분. 답변 1개 저장→개념 1개 연결→주장 1개 생성→지지 또는 반박 근거 연결→원문 복귀. 용어/버튼이 이해되는지 평가 | 설명 없이 수행 가능. 관계 종류와 근거를 사용자가 납득. AI 제안은 승인 전 확정되지 않음 |

| 5. 출시 확인 | Mac 실기기, 설치·CLI 연결, 서명/공증·업데이트·복구 경로, 시작 속도 | 다른 사람 1명에게 약 15분. 설명 없이 폴더 선택→PDF 가져오기→질문→노트 저장. Mac은 해당 기기 사용자 확인 | 지원한다고 표방할 플랫폼에서 설치부터 핵심 흐름 완료. 실패와 지원 한계 문서화 |

피드백 양식은 이것이면 충분하다:

```text
묶음 / 빌드:
논문 / 페이지 / 수행한 행동:
기대한 결과:
실제 결과: (가능하면 화면 1장)
판정: 반드시 수정 / 불편하지만 사용 가능 / 취향
```

번역 의미 판단에는 분야를 아는 사용자의 확인이 필요하다. 성능·저장·토큰 집계의 정확성·경로 경합은 개발자가 자동 검증할 몫이다. 문구와 화면 간격의 취향을 AI 페르소나끼리 반복 평가하며 작업을 무한히 이어가지 않는다.

## 5. 검증 내역과 한계

- `npm run build` 통과. 번들 크기 경고 있음.
- 기존 검사 5개 통과: reading-evidence, anchor-context, translation-request, chat-images, local-paper-digest. 이미지 파일 symlink 검사는 Windows 권한 때문에 생략, junction 경계 검사는 통과했다고 테스트가 보고했다.
- 별도 진단 `tmp/audit-context-2026-09-10.mjs`에서 페이지 본문 누락·9번째 논문 누락·명시적 근거 합계 초과 재현. 임시 파일은 Git에 포함되지 않는다. 위 재현 조건은 본 문서에 기록했다.
- GitHub CLI 조회 기준 최신 `ee056bf` CI는 여전히 실패: https://github.com/help-me-prism/prism/actions/runs/34421941725 . 인계 보고서의 세 플랫폼 임시경로 비교 실패와 같은 실행이다. 이번에는 CI를 수정/재실행하지 않았다. `scripts/test-local-paper-digest.mjs:38`은 resolve한 경로와 realpath를 비교하므로 경로 별칭에 취약하다. 로컬 통과가 CI 해소를 뜻하지 않는다.
- 화면을 새로 조작해 사용성을 승인하지 않았고 실제 모델 품질·장기 토큰량도 새로 측정하지 않았다. 저장/보관함 위험 D와 CLI 외부 설정 유입량은 후속 재현 대상으로 명시했다.

다음 구현은 순서 0과 1을 먼저 묶어 진행하는 것이 좋다. 사용자 피드백은 그 결과물부터 시작하고, 구조 맵·그래프·템플릿의 존폐나 대규모 재작성은 당장 결정할 필요가 없다.
