# Notes 작업 공간 (UI 2차)

2026-09-03, 브랜치 `feat/research-db`. 기능은 유지하고 화면 구조만 다시 잡은 기록이다.

## 왜 바꿨나

1차 UI는 기존 노트 창을 재활용해서 이런 문제가 있었다.

- **지식이 모달 안에 있었다.** 논문 노트는 왼쪽 목록에, 개념·주장·질문은 `연구 지식` 모달 안에 있었다. 같은 볼트의 같은 종류 파일인데 접근 경로가 달랐고, 그래프는 모달 안의 또 다른 모달이었다.
- **버튼이 너무 많고 숨어 있었다.** 툴바에 블록 삽입 11개 + 링크·지식·정리·템플릿·모드 3개 + 연결까지 한 줄에 있었다. 정작 "지금 뭘 해야 하는지"는 어디에도 없었다.
- **모드가 인지 부담이었다.** Live Edit / 읽기 / 분할을 사용자가 골라야 했다.
- **리더와의 관계가 안 보였다.** 노트 창에서 논문 리더로 가는 길이 없었다.

## 지금 구조

```text
┌ rail ┬ tree ─────────┬ tabs ─────────────────────┬ connections ──┐
│ 리더  │ vault-name    │ ● note-a  × │ ● note-b ×  │ 연결 그래프    │
│ 노트  │ 🔍 검색       ├───────────────────────────┤  (2홉 · 인용)  │
│ 정리³ │ + 새 노트     │ 논문                       │ 백링크         │
│ 검색  │ ▾ papers   12 │ 제목                       │ 인용 (자동)    │
│      │   note-a      │ ▾ 속성 7개                 │ 제안           │
│ 연결  │ ▾ concepts  8 │   유형·상태·읽기·범위·관계   │               │
│ 양식  │ ▾ claims    4 │                            │               │
│ 폴더  │ ▾ questions 2 │ 본문 (항상 Live Edit)      │               │
│      │ [정리 대기 3] │ PDF 근거 2                 │               │
└──────┴───────────────┴────────────────────────────┴───────────────┘
│ vault-name · 노드 26 · 이 노트 관계 3 · 백링크 5 · 정리 대기 3 · markdown │
```

- **왼쪽 레일**: 리더 / 노트 / 정리 대기열(배지) / 검색 · 연결 패널 토글 / 양식 / 라이브러리 폴더.
- **트리**: 볼트의 모든 노드를 폴더별로. 링크만 있고 아직 정리 안 한 개념은 기울임체로 흐리게 보인다. 검색창은 입력하면 제목 필터, Enter를 누르면 의미 검색.
- **탭**: 최근 연 노트 8개까지. 논문·개념·주장·질문이 같은 탭 줄에 선다.
- **문서**: 제목 + 접을 수 있는 속성 표 + 본문. 속성 표에는 관계가 행으로 들어가고, 검토 대기 AI 관계는 그 자리에서 승인·거절한다.
- **오른쪽**: 항상 떠 있는 연결 그래프(1~2홉, 인용 겹쳐보기), 백링크, 인용 레이어, 정리 대기열 바로가기.

## UX 규칙

1. **모드 없음.** 본문은 항상 Live Edit이다. 커서가 있는 블록만 Markdown 표기를 보여주고 나머지는 문서로 렌더링한다.
2. **버튼은 지금 할 수 있는 것만.** 문서 상단에는 `리더에서 열기`(논문만) · `링크` · `근거` 세 개와 `…` 메뉴뿐이다. 블록 삽입은 `/`와 본문 아래 `블록 삽입` 하나로 합쳤다.
3. **모달은 양식 관리 하나뿐.** 지식 노트, 그래프, 대기열, 근거 선택은 모두 창 안에서 처리한다.
4. **리더와 왕복이 보인다.** 레일 첫 버튼과 논문 노트의 `리더에서 열기`가 리더 창을 띄우고, 근거 카드를 누르면 PDF 원위치로 간다. 반대로 리더에서 문장을 우클릭해 담은 메모는 논문 노트에 바로 나타난다.
5. **색은 그대로.** 기존 크림·보라 팔레트를 유지하고, 노드 종류만 색 점으로 구분한다(논문 파랑 · 개념 초록 · 주장 황토 · 질문 보라 · 반박 빨강 점선).

## 유지된 계약

화면만 바뀌었고 저장 형식과 IPC는 그대로다. `shared/contracts/*.md`의 관계·캡처·정리·모델 제안·인용 계약은 유효하다. 새로 추가된 것은 두 가지다.

- `reader:open` — 노트 창에서 리더 창을 띄우고, arXiv ID를 주면 그 논문을 연다.
- `MarkdownEditorHandle.openInsertMenu()` — 커서 위치에 맞춰 `/` 블록 메뉴를 연다.

`KnowledgeManager.tsx`는 `NoteDocument.tsx`(문서), `ConnectionsPanel.tsx`(오른쪽), `NotesWindow.tsx`(셸)로 나뉘어 사라졌다. 공통 라벨과 관계 규칙은 `src/knowledgeModel.ts`에 모았다.

## 2026-09-05 손이 덜 가는 구조

노트를 안 쓰게 되는 이유는 하나였다. **쓸 게 너무 많았다.** 실제 Vault에는 관계 0개, 빈 개념 스텁 5개, 예전 양식의 빈 제목 8개만 남아 있었다. 그래서 기계가 쓸 수 있는 것은 전부 기계가 쓰도록 바꿨다.

### 논문 노트는 열면 이미 쓰여 있다

| 섹션 | 누가 | 근거 |
| --- | --- | --- |
| 한눈에 | 자동 | 초록 (모델 있으면 문제·방법·결과로 다시 씀) |
| 내가 헷갈린 것 | 자동 | 이 논문 맥락의 채팅에서 **사용자 질문만**. 반복하면 "2번 물어봄" |
| 내가 주목한 것 | 자동 | 채팅에서 태그한 앵커를 참조 횟수 순으로 |
| 내 생각 | 사용자 | 자동 정리가 절대 건드리지 않음 |
| 메모 | 사용자·리더 | 우클릭 캡처가 쌓임 |

자동 구간은 `<!-- prism:auto ... -->` 마커 안에만 쓴다. 노트를 열면 비용 없는 결정적 갱신이 한 번 돌고, 모델 호출은 `자동 정리 갱신`을 눌렀을 때만 한다. **뽑을 게 없으면 이미 쓴 내용을 지우지 않는다** — 채팅을 잠깐 못 읽어도 노트가 비지 않는다. 계약은 `shared/contracts/paper-digest.md`.

### 링크가 곧 관계

`[[링크]]`를 쓰면 그 자체로 그래프 엣지가 된다(`origin: 'link'`). 관계 유형을 고를 필요가 없고, 나중에 `관계 지정`으로 `정의함`·`지지함` 같은 유형을 붙이면 링크 엣지는 그 자리를 내준다. 링크를 지우면 엣지도 사라지지만, 직접 승인한 유형 관계는 남는다. 링크 엣지는 Markdown에 관계 블록을 만들지 않는다 — 본문의 링크가 이미 사람이 읽는 형태이기 때문이다.

문서의 링크는 클릭하면 그 노트로 이동한다(Alt+클릭은 커서 놓기).

### 트리에서 바로

- 논문·개념·주장·질문 네 폴더는 비어 있어도 항상 보인다. 무엇을 만들 수 있는지가 먼저 보여야 한다.
- 폴더의 `+`로 그 유형의 노트를 바로 만든다.
- 행의 휴지통으로 삭제하고, 알림의 `실행 취소`로 되돌린다. 삭제는 `.prism/trash/knowledge/`로 옮기는 것이라 파일은 남는다.
- `…` 메뉴의 `빈 양식 섹션 정리`는 내용이 하나도 없는 제목만 지운다.

### 쓸 자리를 보여준다

자동 구간이 채워지고 나면 정작 **자기 문장을 어디에 쓰는지**가 안 보인다. 그래서 둘을 더했다.

- 본문 아래 `내 생각 쓰기`를 누르면 `## 내 생각` 바로 아래 빈 줄로 커서가 간다. 논문 노트에만 나온다.
- 비어 있는 `내 생각`·`메모` 섹션에는 회색 안내 문구가 뜬다. **파일에는 아무것도 안 쓴다** — 에디터 장식이라 Obsidian에서 열면 그대로 빈 섹션이다.

PDF 근거 카드는 통째로 렌더된 블록이 됐다. 커서가 들어가지 않으니 옆을 클릭하고 타이핑해도 카드가 깨지지 않고, 카드를 누르면 PDF 원위치로 간다. 카드가 깨지면 그 아래 메모가 승격 대상으로 잡히지 않아 `정리 대기열`이 조용히 비어버리던 문제가 있었다.

### 이번에 고친 버그

- `[[Concepts]]`처럼 **폴더 이름만 적은 링크가 개념 노트로** 만들어지던 문제. 이제 볼트 폴더 이름은 건너뛴다.
- `[[Concepts/generative]]`에서 "개념으로 만들기"를 누르면 `Concepts generative`라는 **경로가 이름에 박힌 노트**가 생기던 문제. 마지막 조각만 이름으로 쓰고, 같은 이름이 있으면 그것을 쓴다.

## 2026-09-05 노드마다 무엇이 자동인가

"열면 이미 쓰여 있다"를 논문 노트에만 적용했더니, 개념·주장·질문은 여전히 빈 양식이었다. 이제 **어떤 노트가 어떤 구간을 스스로 쓰는지**를 `electron/paperDigest.ts`의 `noteAutomation` 표 하나가 정한다. 표에 없는 것은 전부 사용자 것이고 자동 정리가 건드리지 않는다.

| 노드 | 기계가 씀 (열 때마다, 공짜) | 모델이 씀 (`자동 정리 갱신`을 눌렀을 때만) |
| --- | --- | --- |
| 논문 | 내가 헷갈린 것, 내가 주목한 것 | 한눈에 (초록에서 기계가 먼저 쓰고, 모델이 있으면 다시 씀) |
| 개념 | 어디서 나왔나, 대화에서 물어본 것 | 정의 |
| 주장 | 어디서 나왔나, 지지 근거, 반박, 대화에서 물어본 것 | 무엇에 달려 있나 |
| 질문 | 어디서 나왔나, 지금까지 나온 답, 대화에서 물어본 것 | — |

- **모델 구간은 볼트에 있는 재료로만 쓴다.** 노트의 인용문·정의 비교 표 행·링크한 문장, 그리고 링크한 논문 초록에서 그 노트를 언급하는 문장만 넘긴다. 재료가 얇으면 모델은 빈 배열을 돌려주도록 되어 있고, 그러면 **이미 쓰인 내용을 지우지 않는다**.
- **모델이 없으면 모델 구간은 손대지 않는다.** 오늘 CLI가 없다는 것이 어제 쓴 정의가 틀렸다는 뜻은 아니다.

### 대화가 노트를 갱신한다

채팅이 잦아들면(마지막 저장 후 4초) 그 대화가 다룬 노트들이 스스로 따라잡는다 — 대화 맥락에 있던 논문, 그리고 사용자가 이름을 부른 개념·주장·질문. 제목은 머리글자로도 부른다(`Optimal Transport` ↔ `OT`). 모델을 부르지 않는 공짜 갱신이라 배경에서 조용히 돈다. `electron/main.ts`의 `routeChatIntoNotes`.

### 질문에 답을 연결한다

`answers` 관계는 답하는 노트에 저장되기 때문에, 정작 질문 노트에서는 만들 길이 없었다. 질문 노트 속성표의 `답 연결`이 답하는 노트를 고르게 하고 관계는 그쪽에 쓴다.

## 2026-09-05 새로 쓰인 것을 알리는 법, 그리고 속성 다이어트

### 기울임체 대신 "안 읽음" 표시

개념 스텁을 흐린 기울임체로 그리던 규칙(`status: inbox`)은 자동 필기가 생기면서 틀린 말이 됐다. Prism이 방금 정의까지 써넣은 노트가 트리에서는 "아직 안 쓴 노트"처럼 보였다. 이제 흐림 표시는 없고, **자동으로 뭔가 쓰이면 트리 행 오른쪽에 작은 점**이 붙는다. 노트를 열어 맨 아래 `읽었어요`를 누르면 사라진다 — 읽었다고 말할 수 있는 건 사용자뿐이니까.

`is-stub` 클래스는 남아 있다 — 링크만으로 생긴 개념이라는 사실은 여전히 참이고 대기열이 그것으로 판단한다. 기울임체로 그리지 않을 뿐이다.

내용이 지워진 것(빈 섹션 제거)은 알리지 않는다. 새로 채워진 섹션만 표시 대상이다. 표시는 `.prism/cache/auto-unread.json`에 노드별로 쌓이고(`electron/autoUnread.ts`), 지워도 노트는 멀쩡하다.

### 속성은 값이 뭔가를 바꿀 때만 남는다

속성 6~7줄 중 실제로 읽는 코드가 있는 것만 남겼다. 프론트매터 필드는 그대로 두고(Obsidian 호환) 패널에서만 뺀다.

| 노드 | 남은 속성 | 그 값을 읽는 곳 |
| --- | --- | --- |
| 모두 | 상태 | 스텁 판정, 정리 대기열, 열린 질문 목록, 보관됨 숨김 |
| 논문 | + 읽기 | `읽음`으로 바꾸면 모델 관계 제안이 돈다 |
| 주장 | + 출처 · 적용 범위(도메인·조건) | 반박 관계의 조건 차이 경고, 모델 제안 컨텍스트 |

뺀 것: **유형**(제목 위 칩과 중복), **중요도·확신도**(저장만 되고 정렬·필터·경고 어디에도 안 쓰임), **근거 종류**, **프로젝트**, **적용 범위의 가정**. 프론트매터에는 그대로 남는다.


## 2026-09-06 볼트가 커져도 열리게

노드 7개에서는 안 보이던 문제가 있었다. **노트 하나를 읽는 것이 볼트 전체를 읽는 것**이었다. id로 노트를 찾으려면 모든 파일을 파싱해야 했고, 백링크는 그것을 노트마다 한 번씩 했고, 자동 필기 스윕은 그것을 다시 노트마다 한 번씩 했다. 열려 있는 문서는 1.2초마다 디스크에 물었는데 그 질문 한 번이 또 볼트 전체 읽기였다.

바뀐 것은 넷이다.

- **파일은 바뀌었을 때만 다시 읽는다.** 파싱한 형태를 메모리에 두고 `mtime + size`로 판별한다. 두 신호를 쓰는 이유는 각각이 거짓말을 하기 때문이다 — mtime은 옆에 켜둔 Obsidian을 잡고, `onNoteWritten` 훅은 같은 밀리초에 같은 길이로 떨어지는 우리 자신의 연속 저장을 잡는다. 여기서 틀리면 열린 편집기에 옛 글이 보이므로 둘 다 낸다.
- **노트는 찾는 게 아니라 가는 것이다.** 노드가 어느 파일에 사는지는 파일이 옮겨질 때만 바뀌므로 마지막으로 본 경로를 먼저 시도하고, 그 답이 틀렸을 때만 전체를 훑는다.
- **스윕은 맥락을 한 번만 만든다.** `buildDigestContext`가 노드·본문·백링크·관계를 한 번 읽어 모든 노트에 넘긴다. 렌더러도 노트마다 IPC를 부르는 대신 `refreshVaultDigests` 한 번을 부른다.
- **폴링 대신 워처.** 메인 프로세스의 `fs.watch`가 어떤 파일이 움직였는지 알려주고, 자기 파일이 불린 문서만 다시 읽는다. 조용한 볼트는 공짜다.

`npm run bench:vault [노드수]`가 임시 폴더에 실제로 커졌을 때의 볼트를 만들어 옛 모양과 새 모양을 나란히 잰다. 실제 라이브러리는 건드리지 않는다. 숫자를 믿기 전에 **새 백링크 인덱스가 옛 방식과 완전히 같은 답을 내는지 먼저 단언한다.**

| 120 노드 | 지금 | 이전 |
| --- | --- | --- |
| 노트 5개의 백링크 | 82ms · 0 reads | 41,622ms · 72,000 reads |
| Notes 창 열기 (전체 스윕) | 510ms · 438 reads | 약 16분 · 1,728,000 reads |

500 노트에서 스윕은 2.2초이고 노드 수에 선형이다.

## 2026-09-06 대화가 노트를 기억한다

`routeChatIntoNotes`는 규칙으로 기억할 것을 골랐다. 사용자 메시지를 문장으로 쪼개고, 물음표나 의문사가 있는 것만 남기고, 어간으로 묶었다. 질문은 찾지만 대화가 정리한 나머지는 전부 놓치고, 답이 틀린 것으로 밝혀져도 스스로 고치지 못한 채 쌓기만 했다.

이제 **답하고 있는 그 모델이 같은 턴 안에서 판단한다.** 메모리를 가진 어시스턴트들이 실제로 하는 방식이고, 추론이 한 번 더 들지 않는다.

```text
채팅 한 턴
  └ Claude CLI ── Prism MCP 서버(mcpServer.js, Electron을 Node로 실행)
                   ├ search_knowledge / read_note_memory  (읽기)
                   └ remember(node_id, section, lines[])   (쓰기)
```

### 도구가 표현할 수 없는 쓰기는 일어나지 않는다

안전장치는 모델에게 부탁하는 규칙이 아니라 **도구의 스키마**다. `remember`는 노드 id와 섹션 이름만 받는다 — 경로도, 끼워 넣을 Markdown도 받지 않는다. 그래서 사용자가 쓴 곳에 닿을 수 있는 인자 자체가 없다.

1. 섹션 이름이 그 노드 종류에서 대화가 쓸 수 있는 것인지 (`isChatSection`)
2. 쓰기는 `writeAutoSection`을 통과하므로 마커 사이만 바뀌고
3. 저장 직전 `assertOnlyAutoChanged`가 나머지가 그대로인지 확인, 아니면 **저장 거부**

`lines`는 구간을 통째로 대체한다. 최신 상태를 유지한다는 건 더하는 것만큼 **빼는 것**이기도 하다 — 해결된 것, 틀린 것은 빠진 목록으로 다시 보내면 되고, 빈 목록은 구간을 지운다.

### 규칙은 바닥으로 남는다

모델이 도구를 안 부를 수도 있고, CLI를 설정하지 않은 사용자도 있다. 그래서 예전 규칙 기반 추출은 **아직 대화가 손대지 않은 구간만 채우는 바닥**으로 남았다. 대화가 한 번 쓰면 그 구간에서 영구히 물러난다. 어느 구간을 대화가 맡았는지는 `.prism/cache/chat-memory.json`에 쌓이고(`electron/chatMemory.ts`), 지워도 노트는 멀쩡하다 — 규칙이 다시 씨를 뿌릴 뿐이다.

| 노드 | 대화가 쓰는 구간 |
| --- | --- |
| 논문 | 내가 헷갈린 것 |
| 개념 · 주장 · 질문 | 대화에서 물어본 것 |

### CLI별 상태

| CLI | 어떻게 여는가 |
| --- | --- |
| Claude | `--permission-mode plan`은 MCP 도구까지 전부 막는다. 그래서 쓸 도구를 `--allowedTools`로 이름 지어 열고 나머지는 그대로 거부하게 둔다 — 물어볼 사람이 없으면 CLI가 거부한다. 실측: `remember`는 통과, Write/Bash는 차단(모델은 파일을 만들었다고 주장했지만 파일은 없었다) |
| Codex | 읽기 전용 MCP 도구는 그냥 실행하고, **쓰는 도구는 클라이언트에게 물어본다.** `mcpServer/elicitation/request`에 `_meta.codex_approval_kind: "mcp_tool_call"`이 붙어 오고 응답은 `{action: accept\|decline\|cancel}`이다. 그래서 스레드를 `approvalPolicy: 'never'` 대신 `'on-request'`로 돌리고 `electron/codexApproval.ts`가 판단한다 |

Codex를 `on-request`로 바꾼 것이 권한을 넓히지 않는다는 점이 중요하다. `never`는 **우리 도구까지** 같이 거부했고, 지금은 우리 도구만 승인하고 나머지는 전부 거절한다 — 명령 실행·파일 변경·권한 상승은 예전 그대로 막힌다. 승인은 도구를 id가 아니라 **제목**으로 지목하므로 제목은 `noteContract.ts`의 상수 하나다. 그리고 답하지 않으면 턴이 멈추기 때문에 모르는 요청에는 침묵 대신 오류로 답한다 — 예전에는 서버 요청이 id를 달고 와서 **아무도 하지 않은 호출의 응답처럼 보여 조용히 버려졌다.**

MCP 서버는 두 CLI에 다르게 전달한다. Claude는 `--mcp-config`가 가리키는 JSON 파일, Codex는 `thread/start`의 `config.mcp_servers` — 볼트 경로가 스레드마다 정해지므로 후자가 더 맞다. 실행은 둘 다 `ELECTRON_RUN_AS_NODE=1`로 패키징된 `mcpServer.js`라 따로 설치할 것이 없다.

### 지시가 절반이다

모델이 도구를 부르는 것은 두 번째 의도라 시켜야 한다. `noteContract.ts`의 `chatMemoryInstruction`이 Claude에는 `--append-system-prompt`로, Codex에는 `thread/start`의 `developerInstructions`로 붙는다. 실측으로 세 번 고쳤다.

- **부르라고 해야 부른다.** 지시가 없으면 답만 하고 끝났다.
- **언제 부를지도 말해야 한다.** 도구를 지연 로딩하는 CLI에서는 "마지막에 부르라, 다른 도구와 함께 로드하라"까지 적어야 실제로 불렀다.
- **답하는 것과 해결되는 것은 다르다.** 이 말이 없으면 모델이 자기가 설명했다는 이유로 구간을 통째로 비웠다. 지금은 구간의 불변식을 먼저 말한다 — "이 노트에 대해 **아직** 이해하지 못한 것의 목록"이고, 넣고 빼는 기준은 사용자가 한 말뿐이다.

### 검증

`npm run test:capture`의 `test-note-contract.mjs`가 바닥이 씨를 뿌리고 대화가 쓴 뒤에는 물러나는 것을, `test-knowledge-mcp.mjs`가 `remember`가 자기 구간 밖으로 못 나가는 것을 확인한다. `test-codex-approval.mjs`가 승인 판단을 검증한다 — 우리 도구는 승인, 다른 서버의 도구와 우리 서버의 다른 도구는 거절, 명령·파일·권한은 그대로 거부, 모르는 요청은 오류로 응답.

실제 CLI 왕복은 두 CLI 모두 임시 볼트로 확인했다: 한국어로, 사용자 표현으로, 올바른 구간에 쓰고, 다음 턴에 "이제 이해했다"고 한 항목만 지우고 "아직 모르겠다"는 항목은 남겼으며, `prism:mine` 구간은 매번 그대로였다. 작은 모델에서는 지울 것을 안 지우고 넘어가는 일이 있지만, 잃는 방향으로 틀리지는 않았다.
